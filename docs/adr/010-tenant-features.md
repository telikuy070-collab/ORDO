# ADR-010: Tenant Features — Фича-флаги на уровне тенанта

## Статус
Принято

## Контекст
Ordo — мультитенантная платформа (00-vision.md, 01-architecture.md). Каждый колледж (тенант) является изолированным экземпляром платформы. Необходимость в фича-флагах arose из следующих требований:

1. **Онбординг нового колледжа**: некоторые функции должны быть отключены до настройки
2. **A/B тестирование**: эксперименты с функциями для конкретных тенантов
3. **Постепенный запуск**: включение функций по одному колледжу за раз
4. **Отключение проблемных фич**: мгленное отключение, если функция вызывает ошибки
5. **AGENTS.md**: "Фича-флаги — включение/отключение функций" (00-vision.md, стр. 62)

## Решение
Использовать **фича-флаги на уровне тенанта** в Supabase Postgres:

1. **Таблица `tenant_settings`** в Supabase Базе Данных:
   - `id`: UUID
   - `tenant_id`: UUID (связь с тенантом)
   - `feature_name`: string (имя фичи)
   - `value`: JSON (значение флага — boolean, number, string, array)
   - `updated_at`: Date
   - `updated_by`: UUID (кто изменил)

2. **Примеры фича-флагов**:
   - `enable_scheduling` — разрешить создание расписания
   - `enable_import_export` — разрешить импорт/экспорт Excel
   - `enable_analytics` — показывать аналитику
   - `enable_notifications` — отправлять уведомления
   - `enable_auto_generate` — включать автогенерацию черновика (опционально, Sprint 6)

3. **Механизм проверки**:
   - При каждом запросе из PWA (и workspace, и student) проверяется `tenant_id`
   - Supabase RLS политика фильтрует `tenant_settings` по текущему `tenant_id`
   - Frontend читает настройки при инициализации приложения
   - Если фича отключена — соответствующие кнопки и меню скрыты в UI

4. **Admin интерфейс** (для `tenant_admin` и `schedule_owner`):
   - Страница настроек тенанта с переключателями фич
   - Возможность включить/выключить фичу для своего колледжа
   - История изменений фич

5. **Default значения**:
   - При создании нового тенанта все фичи включены по умолчанию
   - Это соответствует философии "с первого дня" (00-vision.md, пункт 2: "Мультитенантность — с первого дня")

## Обоснование
Фича-флаги на уровне тенанта позволяют:
1. **Безопасный онбординг**: новый колледж может начать с базовых функций, постепенно включая новые
2. **Контролируемый запуск**: A/B тестирование без деплоя нового кода
3. **Быстрое отключение**: если фича вызывает баги, её можно выключить одной кнопкой
4. **AGENTS.md compliance**: "Фича-флаги — включение/отключение функций" (00-vision.md)
5. **Мультитенантность**: каждый тенант имеет независимые настройки
6. **Minimal code changes**: добавление новой фичи не требует деплоя, меняется только БД

## Последствия
- Создается миграция `supabase/migrations/001_create_tenant_settings.sql` (или следующая по порядку)
- RLS политика на `tenant_settings` таблице:
  - `tenant_admin` и `schedule_owner` могут читать и менять свои настройки
  - Остальные роли — только чтение (и то, если разрешено)
- Frontend код читает настройки при старте: `const settings = await getTenantSettings()`
- Новые фичи добавляются в список по умолчанию при создании тенанта
- UI компоненты проверяют `settings.enable_<feature>` перед отображением
- История изменений фич хранится в таблице (опционально, через триггеры)

## Альтернативы
- **Фича-флаги на уровне кода** (environment variables): Deploy-time конфигурация. Минусы: требует деплоя для включения/выключения, нет гибкости на уровне тенанта, сложный rollback.
- **Фича-флаги на уровне feature flag сервиса** (LaunchDarkly и т.д.): внешний сервис. Минусы: дополнительная стоимость, зависимость от внешнего сервиса, overkill для проекта.
- **Отсутствие фич-флагов**: все всегда включено. Минусы: нет контроля над onboarding, не можем экспериментировать, сложнее работать с новыми колледжами.

**Выбранный вариант**: Фича-флаги на уровне тенанта в Supabase (рекомендовано 00-vision.md, 01-architecture.md, AGENTS.md).
