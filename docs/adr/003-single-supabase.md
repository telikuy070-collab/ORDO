# ADR-003: Single Supabase

## Статус
Принято

## Контекст
Ordo — мультитенантная платформа для управления расписанием медицинских колледжей. Product vision требует работы с разными типами пользователей: зама, преподаватели, студенты (анонимно), зав. отделением, директор. Каждому типу требуется разный уровень доступа к данным.

Технические требования:
- **Supabase** обеспечивает Postgres + RLS + Auth + Realtime + Edge Functions
- Два PWA (workspace и student) должны работать над одной БД
- Мультитенантность: данные каждого колледжа изолированы через `tenant_id`
- Чистые анонимные студенты (без логина)

## Решение
Один Supabase проект на oba PWA-приложения:

- **Общая инфраструктура**: Postgres 16, Auth, Realtime, Edge Functions (Deno)
- **RLS (Row Level Security)**: включен для всех таблиц с политиками на основе `tenant_id`
- **Auth configuration**:
  - `workspace` PWA использует Auth с email/пароль (для зама, преподавателей, заведующих)
  - `student` PWA использует анонимный доступ (no login required)
- **Multitenant isolation**: every table has `tenant_id` column, RLS политики ограничивают доступ в зависимости от текущего тенанта
- **Edge Functions**: общие функции для обоих приложений, разделение через названия или флаги
- **Realtime**: подписки есть и от workspace, и от student, но с фильтрацией по tenant_id

## Обоснование
Один Supabase проект позволяет:
1. **Единый источник истины**: все данные (расписание, пользователи, нагрузка) в одной БД
2. **Мультитенантность с первого дня**: every table имеет `tenant_id`, RLS работает сразу
3. **Realtime синхронизация**: изменения в workspace мгновенно появляются в student PWA через Realtime каналы (с фильтрацией)
4. **Упрощение операций**: один проект для миграций, один для бэкапов, один для мониторинга
5. **Cost efficiency**: один подписка Supabase вместо двух
6. **AGENTS.md compliance**: "Один Supabase на oba приложения" (AGENTS.md, строка 17)

## Последствия
- Единый проект ID Supabase
- RLS политики на каждую таблицу (требует внимания при создании новых таблиц)
- Два разных способа аутентификации в одном проекте (authenticated + anonymous)
- Realtime каналы с фильтрацией по tenant_id
- Edge Functions общие для обоих приложений
- Миграции применяются к одному проекту (только через миграции, никогда вручную)

## Альтернативы
- **Два Supabase проекта**: отдельные проекты для workspace и student. Минусы: дублирование конфигурации, сложность синхронизации миграций, разные версии РБС, дороже в поддержке.
- **Supabase + внешняя БД**: Supabase только для Auth, своя Postgres. Минусы: потерять Realtime, Edge Functions, упрощенную RLS, лишняя сложность интеграции.

**Выбранный вариант**: Один Supabase проект (рекомендовано AGENTS.md, 00-vision.md, 01-architecture.md).
