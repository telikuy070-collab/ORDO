# ADR-018: Agent Pipeline

## Pipeline — часть инструмента, не архитектуры

Pipeline (Agent Manager, задачи, работы) — это механизм доставки решений, не часть самодостаточной архитектуры Ordo. Pipeline может меняться при смене инструментов, но **архитектурные решения (ADR) должны сохраняться**.

---

## docs/ + AGENTS.md + тесты — гарантируют качество

Качество проекта обеспечивается тройственным соотношением:

1. **docs/** —单一 источник истины (vision, architecture, domain model, rbac, data model).
2. **AGENTS.md** — правила работы агента, конвенции, запреты.
3. **Тесты** — pgTAP для RLS, Vitest для application, Vitest/E2E для presentation.

### Гарантии

| Component | Гарантия |
|---|---|
| docs/ | Актуальная архитектура, RLS, границы |
| AGENTS.md | Правила выполнения, стиль кода |
| Тесты | Функциональная корректность, изоляция |

---

## Миграция при смене инструмента

При переходе с одного Agent Manager на другой или смена системы автоматизации:

1. **Сохранить ADR** — архитектурные решения не зависят от инструмента.
2. **Обновить AGENTS.md** — правила, стек, команды.
3. **Перенести тесты** — pgTAP тесты работают независимо от системы CI/CD.
4. **Обновить скрипты** — `pnpm`, `turbo`, пути к файлам.

### Пример миграции скриптов

```bash
# Было (старый инструмент)
old-tool lint docs/

# Стало (новый инструмент)
pnpm lint docs/
```

## Ревью — человек + второй агент

Все изменения проходят双向 ревью:

1. **Человек** — senior engineer проверяет:
   - Бизнес-логика
   - Безопасность (RLS, данные)
   - Качество кода
   - Соответствие AGENTS.md

2. **Второй агент** — независимый агент проверяет:
   - ADR/RFC соответствие
   - Наличие тестов
   - CI проверки
   - Консистентность документации

### Чек-лист ревью

- [ ] ADR создан/обновлен
- [ ] RFC создан/обновлен (если нужно)
- [ ] Тесты написаны (≥80% domain coverage)
- [ ] CI проходит (typecheck, lint, test)
- [ ] Документация согласована
- [ ] Никаких `any` (кроме обоснованных)
- [ ] Никаких `TODO` в коде

---

## Пайплайн выполнения задач агентом

1. **Читать AGENTS.md** — правила и стек.
2. **Читать ADR** — архитектурный контекст.
3. **Читать задачу** — scope и критерии принятия.
4. **Начинать работу** — соблюдать Clean Architecture.
5. **Проверять перед коммитом** — `pnpm typecheck`, `pnpm lint`, `pnpm test`.
6. **Делать коммит** — conventional commits.
7. **Писать в чат** — результат работы, скриншоты проблем.
