# ADR-004: Anonymous Students

## Статус
Принято

## Контекст
Ordo обслуживает двух пользователей: персонал (с логином) и студентов (анонимно, без логина). Vision документ (00-vision.md) четко определяет: студенты должны иметь мгновенный доступ к расписанию без необходимости регистрации.

Технические требования из AGENTS.md:
- **Никаких pre-commit hooks** (раздел 5)
- **TypeScript strict mode** (раздел 5)
- **Clean Architecture** с изолированными модулями (раздел 4)
- RLS обязателен для каждой таблицы (раздел 5, пункт 141)

## Решение
Студенты работают в режиме **anon** без авторизации:

- **student PWA** не требует логина, вход возможен сразу
- Supabase анонимный ключ (anon key) используется для всех операций чтения
- Для записьных операций (если есть) — только через Service Role Key в Edge Functions
- Все таблицы имеют `tenant_id` с RLS политиками, но для anon-доступа политики разрешают чтение публичных данных
- **Нет сохранения личных данных**: студент не имеет своей страницы, его взаимодействие ограничено просмотром расписания
- Возможность сохранения избранного или истории есть только если студент авторизуется (опционально)

## Обоснование
Режим анонимных студентов позволяет:
1. **Мгновенный доступ**: студент открывает ссылку и сразу видит расписание
2. **Нет барьера входа**: не нужно регистрироваться, подтверждать email
3. **Простота реализации**: RLS политики для anon-역 are проще, чем с полным Auth
4. **Соответствие vision**: "Для студентов (анонимно, без логина)" (00-vision.md, строка 15)
5. **AGENTS.md compliance**: "Анонимные студенты — чистая БД" (01-architecture.md, пункт 5)
6. **Bug factor reduction**: меньше кода авторизации, меньше потенциальных уязвимостей

## Последствия
- Student PWA начинается с пустого экрана и быстрой загрузкой данных
- Supabase anon key хранится в клиенте (это безопасно, так как ограничения через RLS)
- RLS политики должны явно разрешать чтение для anon роли
- workspace PWA использует authenticated пользователей (email/пароль)
- Данные студентов не хранятся в профиле (кроме временного кэша в браузере)
- Возможность позже добавить вход через социальные сети или email (опционально)

## Альтернативы
- **Полный Auth для всех**: требовать вход даже у студентов. Минусы: противоречит vision, увеличивает bounce rate, усложняет onboarding.
- **Социальный вход**: вход через Google/Apple. Минусы: лишние зависимости, противоречит "анонимно, без логина".

**Выбранный вариант**: Анонимные студенты (рекомендовано 00-vision.md, 01-architecture.md, AGENTS.md).
