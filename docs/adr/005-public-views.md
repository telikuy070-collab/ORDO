# ADR-005: Public Views

## Статус
Принято

## Контекст
Ordo имеет два типа приложений с разным уровнем доступа:
- **workspace PWA**: authenticated пользователи (зам, преподаватели, заведующие)
- **student PWA**: анонимные студенты, вход без логина

Студентам нужно просматривать расписание, но не все данные должны быть доступны. Некоторые данные являются публичными, а некоторые — внутренними для колледжа.

## Решение
Использовать **public views** в Supabase Postgres для разделения данных:

- Создавать представления (views) в Supabase, которые не требуют авторизации
- Public views предоставляют только читаемый доступ к расписанию, группам, дисциплинам
- Примеры public views:
  - `public.schedule` — расписание с именами групп, дисциплин, преподавателей (без конфиденциальных данных)
  - `public.groups` — список групп и специальностей
  - `public.rooms` — список аудиторий и корпусов
  - `public.teachers_short` — краткая информация о преподавателях (только имя, должность)
- Все public views имеют фильтрацию по `tenant_id` для мультитенантности
- Student PWA использует anon key и имеет доступ только к public views
- Workspace PWA использует authenticated доступ и имеет доступ ко всем таблицам (включая внутренние)

## Обоснование
Public views позволяют:
1. **Безопасность**: чувствительные данные (оценки, пожелания, личная информация) остаются в приватных таблицах
2. **Простота для student PWA**: anon key + public views = мгновенный доступ без настройки Auth
3. **Чистая RLS**: отдельные политики для public views и основных таблиц
4. **AGENTS.md compliance**: "Анонимные студенты — чистая БД" (01-architecture.md)
5. **Minimal surface area**: student PWA имеет минимальный доступ к БД, что снижает риск утечек данных

## Последствия
- Дополнительные view-объекты в Supabase (не увеличивают стоимость significantly)
- Student PWA запрашивает данные только из public views
- Workspace PWA продолжает использовать прямые таблицы с RLS
- Миграции включают создание view вместе с таблицами
- Обновление public views требует создания новой миграции
- Нужно поддерживать синхронизацию структуры view с доменными сущностями

## Альтернативы
- **Резервные API endpoints**: separate endpoints для student vs workspace. Минусы: дублирование логики, больше кода, потенциально больше уязвимостей.
- **Full RLS с ролями**: одна таблица, разные RLS политики в зависимости от роли. Минусы: сложность поддержки, легко ошибиться с политикой, переполнение политик Postgres (максимум 15 на таблицу).

**Выбранный вариант**: Public views (рекомендовано 01-architecture.md, 03-rbac.md, 00-vision.md).
